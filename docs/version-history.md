# バージョン履歴

KAGURA DB の各バージョンの変更内容をまとめています。最新バージョンの区分（メジャー/マイナー/ビルドの内訳）は [README.md](../README.md) 上部を参照してください。

バージョン表記: **A.B.C**

| 区分 | ルール |
|------|-------|
| **A（メジャー）** | 破壊的変更・旧バージョンとの非互換が生じたとき +1 |
| **B（マイナー）** | 破壊的変更を伴わない新機能追加のとき +1 |
| **C（ビルド）** | 規模に関わらず何らかの変更・修正を加えたとき +1 |

| バージョン | 主な変更内容 |
|-----------|-------------|
| **4.11.0** | 【新機能】`4.10.0` のバックアップ／復元に **Web 管理 UI と REST エンドポイント**を追加。`db_client` に `backup_handlers` モジュールを新設し、`axum` の `multipart` 機能を有効化。エンドポイント（すべて **管理者ロール `kagura` のみ**・**トランザクション中は `409`**・**`RESTORE` 適用後は `409`**＝要再起動）: `POST /backup`（サーバー上にバックアップ作成。省略時は設定の保存先。`auto_save` で現状態を確定してからアーカイブ）／`GET /backup`（保存先の `kagura-backup-*.kbak` 一覧。各ファイルの `manifest` 要約＝作成日時・KAGURA バージョン・件数・`auth` 同梱有無・`WITH KEY` 有無・キー指紋、および現在のマスターキー指紋を返す。壊れたファイルも一覧自体には出す）／`GET /backup/download?name=`（`.kbak` を `application/octet-stream` でダウンロード。`name` は `kagura-backup-` で始まり `.kbak` で終わる単一ファイル名のみ許可。`/`・`\`・`..` を含むと `400`）／`POST /backup/restore`（保存先の `.kbak` を `{ "name": ..., "old_key"?: ... }` で復元）／`POST /backup/restore/upload`（`multipart/form-data` の `file` フィールドに `.kbak`、任意の `old_key` フィールド。一時ファイルへ書き出してから復元し削除。本文上限はこのルートのみ 4 GiB）。復元はいずれも `db_engine::backup::restore` を使い、現ファイルを `pre-restore-<timestamp>/` へ退避してから配置し、`restore_pending` を立てる。`GET`/`PUT /settings` に `backup_dir`（空＝ `<DB_FILE のディレクトリ>/backups`）・`backup_max_generations`（既定7）・`backup_retention_days`（既定30）と、解決後の `backup_dir_resolved` を追加。`PUT` での変更は**管理者ロールのみ**で `<DB_FILE>.backup.json` へ永続化する。Web 管理 UI（`/ui`）の設定ビューに「バックアップ／復元」カードを追加（今すぐバックアップ／`WITH KEY`・`WITHOUT AUTH` チェックボックス、保存先ディレクトリと世代管理の入力、保存先のバックアップ一覧＋ダウンロード＋名前指定で復元、`.kbak` アップロードで復元、マスターキー表示ボタン）。`4.10.0` の SQL `BACKUP`/`RESTORE` 文・`kdb backup`/`restore`/`keyinfo` CLI・`.kbak` フォーマット・マスターキーの扱い（非同梱・`WITH KEY`・`OLD KEY`・リキー・メジャーバージョン非互換の拒否）はいずれも不変。統合テストを新規5件追加（REST の作成／一覧／ダウンロード／パストラバーサル拒否／名前指定復元＋復元後 409、`/settings` の世代設定フィールドの往復と永続化）。全クレートの `Cargo.toml` を `4.11.0` に同期 |
| **4.10.0** | 【新機能】バックアップ／復元機能を追加。`.kdb` 本体（暗号化されたまま）・サイドカーファイル（`*.indexes.json` / `*.schema.json` / `*.memory.json`）・`auth.json`（既定同梱・`WITHOUT AUTH` で除外）を、`manifest.json`（形式バージョン・KAGURA バージョン・作成日時・作成者・レコード件数・マスターキー指紋・各ファイルの SHA-256・`WITH KEY` 時のみ旧マスターキー hex64）付きの1つの `.kbak` アーカイブにまとめる（依存ライブラリなしの独自コンテナ形式・非圧縮。`.kdb` が暗号化済みで圧縮の余地がほぼないため。全ファイルを SHA-256 で完全性検証）。**別サーバーや新規／再インストール環境でも `.kbak` から復旧できる**ことが主眼。SQL 文 `BACKUP TO '<保存先>' [WITH KEY] [WITHOUT AUTH]` / `RESTORE FROM '<.kbak>' [OLD KEY '<hex64>']`（`/sql`・Web UI の SQL Query ビュー）と、`kdb backup` / `kdb restore` / `kdb keyinfo` CLI（稼働中サーバー経由＋サーバー停止中の `--direct --env-file` 直接ファイル操作）。実行できるのは**管理者ロール `kagura` のみ**、**トランザクション中は `409`**。マスターキー本体はアーカイブに含めない（`.kdb` は `HChaCha20(マスターキー, ファイルsalt)` で暗号化されており、`salt` は `.kdb` に入るがキー本体はプログラム内にもデータ内にも無い）ため、`.kbak` 単体では復元できず、(1) `WITH KEY` で `manifest` にキーを同梱するか、(2) `RESTORE ... OLD KEY '<hex64>'` で作成時キーを渡すか、(3) 復元先で同じ `KAGURA_MASTER_KEY` を用意する、のいずれかが必要。復元先の現マスターキーが作成時と指紋一致しない場合、旧キーで `.kdb` を全レコード復号し、復元先の現キー（新ランダム salt）で再暗号化（リキー）してから配置する。`RESTORE` は現ファイルを `pre-restore-<timestamp>/` へ退避してから置き換え、適用後は稼働中プロセスが書き込み系リクエストを `409` で拒否し `auto_save` を抑止する（メモリ上の復元前データで `.kdb`/JSON を上書きしないため。`SELECT` は可能）。反映にはサーバー再起動が必要。**メジャーバージョンが異なる `.kbak` は復元を拒否**（`3.x` を `4.x` へ等）。サーバーローカルの保存先（`BACKUP TO` にディレクトリを渡したときの出力先）は、バックアップ成功のたびに**世代管理**で剪定する（保持世代数の上限＝既定7・保持日数＝既定30、`0` で無制限。設定は `<DB_FILE>.backup.json` に永続化。ダウンロード出力や `--direct` 出力は対象外）。マスターキー表示エンドポイント `GET /settings/master-key`（管理者ロールのみ。呼び出すと監査ログに「マスターキーを表示しました」とだけ記録し、**キー値はログに残さない**）と `kdb keyinfo [--reveal]` を追加。実装: `db_engine` に `sha256`（FIPS 180-4 の依存なし実装）・`backup`（コンテナ read/write ＋ 高水準の `data_file_specs` / `restore` / `prune_generations`）モジュール、`db_client` に `backup`（SQL パース＋実行オーケストレーション）・`backup_settings`（サイドカー）・`sql_handlers` のディスパッチ、`kdb_cli` に `backup_cmd`。`AppStateInner` に `restore_pending` フラグ、`AuthState::file_path()` アクセサを追加。ユニット・統合テストを新規24件追加。**この版の範囲**: Web 管理 UI のバックアップカードと REST エンドポイント（`POST /backup` / `GET /backup` / `POST /backup/restore`）、`PUT /settings` からの世代設定変更は後続バージョンで追加予定。全クレートの `Cargo.toml` を `4.10.0` に同期 |
| **4.9.3** | 【バックアップ機能の基盤・挙動無変更】これから追加するバックアップ／復元機能（`.kdb` ＋ サイドカーファイル ＋ `auth.json` を1アーカイブに束ね、別サーバーや新規／再インストール環境でも `.kbak` から復旧できるようにする）の土台として、`db_engine` に既存挙動を変えない追加のみを行った。(1) マスターキーのユーティリティ `kdb_store::parse_master_key_hex`（hex64 の厳密パース。桁数不足・16進以外はエラー）／`resolve_master_key`（現プロセスのキー）／`master_key_hex`／`master_key_fingerprint`・`fingerprint_of_key`（`HChaCha20(key, 0^16)` の先頭16バイトを hex 表記した非可逆な指紋。バックアップ作成時のキーと復元先サーバーのキーが一致するかの突き合わせに使い、キー本体は復元できない）。(2) `KdbFile::open_with_key` / `create_with_key`（マスターキーを引数で明示指定して `.kdb` を開閉。既存の `open`/`create` は新関数へ委譲するだけで、`KAGURA_MASTER_KEY` を参照する従来動作は不変）。(3) `kdb_store::rekey_kdb(path, old_key, new_key)`（`.kdb` を旧キーで全レコード復号し、新しいランダム salt ＋ 新キーで再暗号化して同じパスへ書き戻すリキー処理。復元先のマスターキーが作成時と異なる場合に使用。誤った旧キーは最初のレコード復号失敗で弾き、元ファイルは破壊しない）。`db_engine/src/tests.rs` にユニットテストを新規4件追加（hex パース・指紋の安定性とキー依存性・リキー往復・誤キー拒否）。API・SQL・`.kdb`/JSON フォーマット・`auth.json`・`kdb` CLI の挙動には一切影響しない。全クレートの `Cargo.toml` を `4.9.3` に同期 |
| **4.9.2** | 【ドキュメント整理】肥大化した `README.md` 下部の「バージョン履歴」テーブルをこのファイル（`docs/version-history.md`）へ分離し、README 側には区分（A.B.C）の説明とこのファイルへの参照リンクのみを残した。`CLAUDE.md` の必須ワークフローも、以後は新しいバージョン行をこのファイルの変更履歴テーブル先頭へ追記するよう更新。README の「📚 ドキュメント」表にもエントリを追加。ドキュメントのみの変更で、コード・API・`.kdb`/JSON フォーマット・`kdb` CLI の挙動には一切影響しない。全クレートの `Cargo.toml` を `4.9.2` に同期 |
| **4.9.1** | 【バグ修正・UIのみ】Web 管理 UI（`/ui`）の設定・ログ・レコード一覧・DB Info の各ビューが縦スクロールできず、画面に収まらない部分（設定画面の「スキーマ管理」「全データオンメモリ」カードなど）が表示・操作できなくなっていた不具合を修正。原因は `showView()` が表示中ビューの `display` を `''`（＝`block`）にしていたことで、ビューの入れ子フレックス・スクロール領域（`.info-panel` 等の `flex:1; overflow:auto`）が高さ制約を失い、外側の `overflow:hidden` にクリップされていた。`display:'flex'` を設定し、`#viewRecords` にも他ビューと同じ `flex:1; overflow:hidden; flex-direction:column` を付与して統一。`db_client/src/ui.html` のみの変更で、API・SQL・`.kdb`/JSON フォーマット・`kdb` CLI の挙動には影響しない。全 `Cargo.toml` を `4.9.1` に同期 |
| **4.9.0** | SQL トランザクション（`BEGIN`/`BEGIN TRANSACTION`/`START TRANSACTION`・`COMMIT`・`ROLLBACK`）を追加。複数の `INSERT`/`UPDATE`/`DELETE` を1単位にまとめ、`COMMIT` でまとめて永続化、`ROLLBACK` で `BEGIN` 前へ戻す。同時に開けるのは1つで `BEGIN` したログインユーザーが所有者。開いている間、他ユーザーの書き込み・別の `BEGIN`・所有者以外の `COMMIT`/`ROLLBACK` は `409`、DDL（ユーザー/インデックス/スキーマ管理）も `409`。トランザクション中の `SELECT` は未コミット値が見える（read uncommitted 相当）。`BEGIN`〜`COMMIT` 間は `.kdb`/JSON を書き換えず `COMMIT` 時に一度だけ `compact` で永続化し、`ROLLBACK` はディスクから読み直す（サイドカーの索引・スキーマ定義・「全データオンメモリ」設定も復元）。無操作 300 秒で次の書き込み系リクエスト時に自動 `ROLLBACK`。容量制限モードでもトランザクション中はメモリの追い出しを停止（`COMMIT`/`ROLLBACK` 後に削り直す）。実装は `db_client` のディスパッチ層（`db_engine` には追い出し停止フラグのみ追加）と `bootstrap.rs`（再ロード）。v1 の制限: `/sql`（Web UI の SQL Query ビュー）からのみ。`kdb` CLI・`db_ffi` は未対応。`COMMIT` 時の `.kdb` 書き込みの原子性は既存の `UPDATE`/`DELETE` と同レベル。テスト新規6件。全 `Cargo.toml` を `4.9.0` に同期 |
| **4.8.0** | 「全データオンメモリ」の ON/OFF を切り替え可能にした（既定 ON ＝ 従来どおり全レコードをメモリ常駐・オーバーヘッドなし）。OFF にすると容量制限モードになり、上限（絶対バイト数 `500MB`/`5GB`、または搭載物理メモリに対する割合 `20%`。Linux は `/proc/meminfo` から取得）を超える分は、直近使われていない行の列データから `.kdb` へ退避してメモリ使用量を抑える。退避された行はアクセス時に `KdbFile::read_record_at`（バイトオフセット指定の単体読み直し）で `.kdb` から復元し、再アクセスで立ち退き順が末尾へ移動する（実質LRU）。`db_engine` に `MemoryPolicy`/`MemorySizeSpec`/`MemoryStats`・`Database::set_memory_policy`/`memory_policy`/`memory_stats` を新設。公開API（`get`/`get_by_label`/`insert`/`update` 等）のシグネチャは変えず、内部可変キャッシュ `Mutex<MemCache>` と行ごとの `loaded` フラグで実現。既定（`all_in_memory=true`）のときはこのキャッシュに一切触れずインラインの列をそのまま返す高速パスで、オーバーヘッドはない。`GET`/`PUT /settings` に `all_in_memory`（bool）・`memory_limit`（`{"kind":"bytes"\|"percent","value":n}`）・`memory_limit_spec`（`"500MB"`/`"2GB"`/`"20%"` の文字列）を追加。全データオンメモリ設定の変更は**管理者ロール `kagura` のみ**（他ユーザーは `403`）、かつ **`.kdb` モードのみ**（JSON モードは `400`。退避先のランダムアクセス機構が `.kdb` にしかないため）。設定はサイドカーファイル `<DB_FILE>.memory.json` に保存し、二次インデックス・スキーマ定義と同様、`.kdb`/JSON 本体は無変更で起動時に読み込んで適用する（スキーマ強制スイッチと違い、こちらは運用上の恒久設定なので再起動をまたいで保持）。`kdb in-memory-mode enable\|disable` / `kdb in-memory-size <値>` を新設（`PUT /settings` を叩く）。Web UI（`/ui` 設定画面）に「全データオンメモリ」トグルと上限入力を追加。**v1 の制限**: 容量制限モードでも、サーバー起動時（`.kdb` 全読み込み）と全件対象の操作（`SELECT * FROM label.*`・`GET /records`・UPDATE/DELETE 後の `.kdb` コンパクション）では一時的に全レコードがメモリに載る（`.kdb` が追記WAL＋全書き直し方式のため）。恒常的なメモリ使用量と参照系クエリのメモリは制限され、`INSERT` のみ／対象を絞った `SELECT` のワークロードでは完全に効果がある。`db_engine`/`db_client` にユニット・統合テストを追加（新規17件）。全クレートの `Cargo.toml` を `4.8.0` に同期 |
